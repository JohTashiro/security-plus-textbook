メモリインジェクションMemory injection Memory injection Inyección en memoria

メモリに悪意あるコードを潜り込ませる

Slips malicious code into memory

Introduce código malicioso en la memoria

代表例ExamplesEjemplos

  • eval() の悪用
  • Code injected into an input field
  • Abusing eval()
  • Código inyectado en un campo de entrada
  • Abuso de eval()
詳しく（仕組みと対策）Details: how it works & defensesDetalles: cómo funciona y defensas

仕組み

  1. 攻撃者は、すでに動いている正規のプロセスのメモリに、自分のコードを書き込む（DLLインジェクション、プロセスホローイングなど）
  2. 書き込んだコードを、そのプロセスの一部として実行させる
  3. 正規のプログラムの名前と権限で動くため、セキュリティソフトに見つかりにくい
  4. ディスクにファイルを残さないファイルレス攻撃にもよく使われる

実例

Cobalt Strike などの攻撃ツールには、正規のプロセスにコードを注入して動く機能がある。こうしたツールは、多くのランサムウェア攻撃で、侵入後の遠隔操作に悪用されている。

兆候

  • 普段は通信しない正規のプロセス（メモ帳や rundll32 など）が外部と通信している
  • プロセスのメモリ上に、実行可能なコード領域が不自然に作られている

対策：予防

  • OSのメモリ保護機能（DEP・ASLR）を有効にし、パッチを当てる
  • 最小特権で、他のプロセスのメモリに書き込める権限を制限する
  • アプリケーション許可リストで、不審なプログラムの実行を止める

対策：検知

  • EDR で、プロセス間のメモリ書き込みや不審なスレッドの作成を検知する
  • メモリフォレンジック（メモリの中身の解析）で、ファイルを残さない攻撃を調べる

対策：対応

  • 端末を隔離し、電源を切る前にメモリの内容を保全する（ファイルレス攻撃の証拠はメモリにしかない）
  • 感染経路を調べて端末を再構築する

試験のポイント

メモリインジェクションは、正規プロセスのメモリにコードを入れて実行させる攻撃。ファイルが残らないことが多いので、検知は EDR、調査はメモリの保全が鍵。

How it works

  1. The attacker writes its own code into the memory of a legitimate, running process (DLL injection, process hollowing...)
  2. The injected code is then run as part of that process
  3. Because it runs under a trusted program's name and rights, security tools struggle to spot it
  4. It's a favourite of fileless attacks that leave nothing on disk

Real-world case

Attack tools such as Cobalt Strike can inject code into legitimate processes. Such tools have been abused for post-intrusion remote control in many ransomware attacks.

Warning signs

  • A legitimate process that normally never talks to the network (Notepad, rundll32...) is communicating externally
  • Executable regions appear unexpectedly in a process's memory

Defense: prevent

  • Enable OS memory protections (DEP, ASLR) and keep patching
  • Use least privilege to limit who can write into other processes' memory
  • Application allow lists stop suspicious programs from running

Defense: detect

  • EDR detects cross-process memory writes and suspicious thread creation
  • Memory forensics (analysing memory contents) investigates attacks that leave no files

Defense: respond

  • Isolate the host and capture memory before powering off — fileless evidence lives only in RAM
  • Trace the infection path and rebuild the host

Exam tip

Memory injection puts code into a legitimate process's memory and runs it there. It often leaves no files, so detection relies on EDR and investigation on preserving memory.

Cómo funciona

  1. El atacante escribe su código en la memoria de un proceso legítimo en ejecución (inyección de DLL, process hollowing...)
  2. Después hace que ese código se ejecute como parte del proceso
  3. Como funciona con el nombre y los derechos de un programa de confianza, a las herramientas de seguridad les cuesta detectarlo
  4. Es habitual en ataques sin archivos (fileless) que no dejan nada en el disco

Caso real

Herramientas de ataque como Cobalt Strike pueden inyectar código en procesos legítimos. Se han usado de forma abusiva para el control remoto tras la intrusión en muchos ataques de ransomware.

Señales de alerta

  • Un proceso legítimo que normalmente no usa la red (Bloc de notas, rundll32...) se comunica con el exterior
  • Aparecen de forma inesperada regiones ejecutables en la memoria de un proceso

Defensa: prevenir

  • Activar las protecciones de memoria del sistema (DEP, ASLR) y mantener los parches
  • Usar el mínimo privilegio para limitar quién puede escribir en la memoria de otros procesos
  • Las listas de aplicaciones permitidas impiden ejecutar programas sospechosos

Defensa: detectar

  • El EDR detecta escrituras de memoria entre procesos y la creación de hilos sospechosos
  • La forense de memoria (análisis de su contenido) investiga ataques que no dejan archivos

Defensa: responder

  • Aislar el equipo y capturar la memoria antes de apagarlo: las pruebas de un ataque sin archivos solo están en la RAM
  • Rastrear la vía de infección y reconstruir el equipo

Clave para el examen

La inyección en memoria mete código en la memoria de un proceso legítimo y lo ejecuta allí. A menudo no deja archivos: la detección depende del EDR y la investigación de conservar la memoria.

タイムオブユースTime-of-use (TOU) Time-of-use (TOU) Tiempo de uso (TOU)

確認後〜使用時までに状態が変わる

State changes between the check and the time of use

El estado cambia entre la comprobación y el momento de uso

代表例ExamplesEjemplos
  • ログアウト後のセッション
  • 競合状態
  • Session still alive after logout
  • Race condition
  • Sesión activa tras cerrar sesión
  • Condición de carrera
詳しく（仕組みと対策）Details: how it works & defensesDetalles: cómo funciona y defensas

仕組み

  1. プログラムがチェックした内容（ファイル、権限、セッション）を、後で使う時点の状態を確認しないまま使う
  2. 攻撃者は、使う直前までに対象を変える（ファイルを別のものへのリンクに置き換える、権限が外れた後もセッションを使い続ける）
  3. プログラムは変わってしまった対象に対して、元の権限のまま処理を行う

実例

2016年の Dirty COW（CVE-2016-5195）は Linux カーネルの競合状態の脆弱性で、一般ユーザーが本来書き込めない読み取り専用のファイルを書き換え、root 権限を得ることができた。

兆候

  • ログアウトや権限の削除をした後にも、そのセッションでの操作が記録される
  • システムファイルが、権限のない利用者の操作で変更されている

対策：予防

  • 使う直前にもう一度確認するか、確認と使用を不可分にする
  • 権限の削除やログアウト時に、セッションやトークンをすぐに無効化する
  • OSのパッチを当てる（カーネルの競合状態はパッチでしか直せない）

対策：検知

  • コードレビューや静的コード分析で、確認と使用がずれる箇所を見つける
  • ファイル完全性監視で、システムファイルの予期しない変更を検知する

対策：対応

  • パッチを当て、権限が乱用されていないかログで確認する

試験のポイント

TOCTOU の「使う」側。確認した後で状態が変わるのが問題。Time-of-check とセットで出題されるので、どちらも「競合状態」の一種と覚える。

How it works

  1. The program uses something it checked earlier (a file, a permission, a session) without re-checking its state at the time of use
  2. Before that moment, the attacker changes the target — swapping a file for a link elsewhere, or keeping a session alive after the rights were removed
  3. The program acts on the changed target with the original privileges

Real-world case

Dirty COW (CVE-2016-5195) in 2016 was a race condition in the Linux kernel that let an ordinary user overwrite read-only files and gain root.

Warning signs

  • Actions are still logged for a session after logout or after the user's rights were removed
  • System files were changed through actions by an unprivileged user

Defense: prevent

  • Re-check right before use, or make the check and the use indivisible
  • Invalidate sessions and tokens immediately on logout or when rights are removed
  • Patch the OS — kernel race conditions can only be fixed by patching

Defense: detect

  • Code review and static analysis find places where check and use drift apart
  • File integrity monitoring detects unexpected changes to system files

Defense: respond

  • Apply the patch and check the logs for abuse of privileges

Exam tip

The "use" side of TOCTOU: the problem is that state changes after the check. It's tested together with time-of-check — remember both as kinds of race condition.

Cómo funciona

  1. El programa usa algo que comprobó antes (un archivo, un permiso, una sesión) sin volver a comprobar su estado en el momento de usarlo
  2. Antes de ese momento, el atacante cambia el objetivo: sustituye un archivo por un enlace a otro sitio o mantiene viva una sesión tras perder los permisos
  3. El programa actúa sobre el objetivo modificado con los privilegios originales

Caso real

Dirty COW (CVE-2016-5195), en 2016, fue una condición de carrera del núcleo de Linux que permitía a un usuario corriente sobrescribir archivos de solo lectura y obtener privilegios de root.

Señales de alerta

  • Siguen registrándose acciones de una sesión después de cerrarla o de retirar los permisos al usuario
  • Archivos del sistema modificados por acciones de un usuario sin privilegios

Defensa: prevenir

  • Volver a comprobar justo antes de usar, o hacer indivisibles la comprobación y el uso
  • Invalidar sesiones y tokens en cuanto se cierra sesión o se retiran permisos
  • Parchear el sistema: las condiciones de carrera del núcleo solo se corrigen con parches

Defensa: detectar

  • La revisión de código y el análisis estático encuentran puntos donde comprobación y uso se desfasan
  • La supervisión de integridad de archivos detecta cambios inesperados en archivos del sistema

Defensa: responder

  • Aplicar el parche y revisar los registros en busca de abuso de privilegios

Clave para el examen

Es el lado del «uso» de TOCTOU: el problema es que el estado cambia después de comprobarlo. Se pregunta junto con el tiempo de comprobación; recuerda ambos como tipos de condición de carrera.

  • Double transfer
  • Sustitución de un archivo

詳しく（仕組みと対策）Details: how it works & defensesDetalles: cómo funciona y defensas

仕組み

  1. プログラムは、処理の前に条件をチェックする（残高は足りるか、ファイルにアクセスしてよいか）
  2. 攻撃者は、チェックが終わってから実際に使われるまでのわずかなすき間を狙う
  3. そのすき間に、同時に別の要求を送る・ファイルを差し替える
  4. チェックの結果は古くなっているのに、プログラムはそのまま処理を進めてしまう（競合状態）

実例

2015年、研究者の Egor Homakov は、Starbucks のギフトカード間の残高移動に同時に複数の要求を送ると、残高チェックをすり抜けて残高を増やせることを報告した。

兆候

  • 同じ取引が、ほぼ同時刻に重複して記録される
  • 残高や在庫がマイナスになる、計算が合わない

対策：予防

  • チェックと処理を1つの不可分な操作にまとめる（ロック、データベースのトランザクション）
  • ファイルは名前ではなく、開いたハンドルで確認・操作する
  • 同じ要求を2回処理しない仕組み（重複防止のキー）を入れる

対策：検知

  • コードレビューや静的コード分析で、チェックと処理が離れている箇所を見つける
  • 同時に大量の要求を送るテスト（動的テスト）で競合状態を確認する

対策：対応

  • 重複した取引を取り消し、該当する処理を修正する

試験のポイント

TOCTOU（チェックした時点と使う時点のずれ）の「チェック」側。答えは「ロック」「アトミックな処理」。競合状態（レースコンディション）という言葉とセットで覚える。

How it works

  1. A program checks a condition before acting — is the balance sufficient, may this file be accessed?
  2. The attacker targets the tiny gap between the check and the actual use
  3. In that gap it fires simultaneous requests or swaps a file
  4. The check result is now stale, but the program carries on anyway — a race condition

Real-world case

In 2015 researcher Egor Homakov reported that sending several simultaneous balance-transfer requests between Starbucks gift cards slipped past the balance check and created extra credit.

Warning signs

  • The same transaction is recorded twice at almost the same moment
  • Balances or stock go negative; totals don't add up

Defense: prevent

  • Make the check and the action one indivisible (atomic) operation — locks, database transactions
  • Check and operate on files through an open handle rather than by name
  • Prevent processing the same request twice (idempotency keys)

Defense: detect

  • Code review and static analysis find places where check and use are far apart
  • Tests that fire many simultaneous requests (dynamic testing) expose race conditions

Defense: respond

  • Reverse duplicated transactions and fix the code

Exam tip

The "check" side of TOCTOU (the gap between time of check and time of use). Answers: locks, atomic operations. Learn it together with the term race condition.

Cómo funciona

  1. Un programa comprueba una condición antes de actuar: ¿hay saldo suficiente?, ¿se puede acceder a este archivo?
  2. El atacante apunta al pequeño hueco entre la comprobación y el uso real
  3. En ese hueco envía solicitudes simultáneas o sustituye un archivo
  4. El resultado de la comprobación ya no es válido, pero el programa sigue adelante: una condición de carrera

Caso real

En 2015, el investigador Egor Homakov informó de que enviar a la vez varias solicitudes de transferencia de saldo entre tarjetas regalo de Starbucks esquivaba la comprobación del saldo y generaba crédito adicional.

Señales de alerta

  • La misma transacción se registra dos veces casi al mismo tiempo
  • Saldos o existencias quedan en negativo; las cuentas no cuadran

Defensa: prevenir

  • Convertir la comprobación y la acción en una sola operación indivisible (atómica): bloqueos, transacciones de base de datos
  • Comprobar y operar sobre archivos mediante un descriptor abierto, no por su nombre
  • Evitar procesar dos veces la misma solicitud (claves de idempotencia)

Defensa: detectar

  • La revisión de código y el análisis estático encuentran puntos donde comprobación y uso están separados
  • Las pruebas que lanzan muchas solicitudes simultáneas (pruebas dinámicas) revelan condiciones de carrera

Defensa: responder

  • Anular las transacciones duplicadas y corregir el código

Clave para el examen

Es el lado de la «comprobación» de TOCTOU (el hueco entre el momento de comprobar y el de usar). Respuestas: bloqueos, operaciones atómicas. Apréndelo junto con condición de carrera.

詳しく（仕組みと対策）Details: how it works & defensesDetalles: cómo funciona y defensas

仕組み

  1. 攻撃者が、ソフトウェア会社の開発環境や配布サーバーに侵入する
  2. 正規の更新プログラムに、悪意のあるコードを紛れ込ませる
  3. 更新は正規の署名付きで配布されるため、利用者は信頼してインストールしてしまう
  4. 多数の利用者の環境に一斉に入り込む（サプライチェーン攻撃）

実例

2020年に発覚した SolarWinds 事件では、IT管理ソフト Orion の正規アップデートにバックドア（SUNBURST）が仕込まれた。約1万8千の組織がこの更新をダウンロードし、米国の政府機関なども被害を受けた。

兆候

  • 更新後に、ソフトが見慣れない外部サーバーと通信を始める
  • ベンダーや公的機関から侵害の発表がある

対策：予防

  • コード署名の検証に加え、更新の配布元とハッシュ値を確認する
  • 重要な更新は、まず検証環境で動作と通信を確認してから展開する
  • ベンダーのセキュリティ体制を評価し、ソフトの部品表（SBOM）を求める
  • 管理ソフトには最小限の権限とネットワーク接続だけを与える

対策：検知

  • 更新後の通信や振る舞いの変化を EDR／ネットワーク監視で検知する
  • パッケージモニタリングや脅威情報で、侵害された更新の情報を早く知る

対策：対応

  • 影響を受けたバージョンを特定して隔離・削除し、ベンダーの指示に従う
  • そのソフトが使えた認証情報を変更し、侵入の痕跡を調べる

試験のポイント

正規の署名がある更新でも安全とは限らない、というのがポイント。サプライチェーン攻撃の代表例として SolarWinds を覚える。

How it works

  1. The attacker breaks into a software vendor's build environment or distribution servers
  2. Malicious code is slipped into a legitimate update
  3. The update ships with a valid signature, so customers trust it and install it
  4. It lands in many customers' environments at once — a supply chain attack

Real-world case

In the SolarWinds incident uncovered in 2020, a back door (SUNBURST) was planted in legitimate updates for the Orion IT management software. About 18,000 organisations downloaded the update, and US government agencies were among the victims.

Warning signs

  • After an update, the software starts talking to unfamiliar external servers
  • The vendor or public authorities announce a compromise

Defense: prevent

  • Verify code signing and also the update's source and hash
  • Roll out important updates to a test environment first and watch their behaviour and traffic
  • Assess vendors' security and ask for a software bill of materials (SBOM)
  • Give management software only the minimum privileges and network access it needs

Defense: detect

  • EDR and network monitoring detect changes in traffic or behaviour after updates
  • Package monitoring and threat intelligence give early warning of compromised updates

Defense: respond

  • Identify, isolate and remove affected versions; follow the vendor's guidance
  • Change credentials the software could use and hunt for signs of intrusion

Exam tip

Key point: even an update with a valid signature isn't guaranteed safe. Remember SolarWinds as the textbook supply chain attack.

Cómo funciona

  1. El atacante entra en el entorno de compilación o los servidores de distribución de un proveedor de software
  2. Introduce código malicioso en una actualización legítima
  3. La actualización se distribuye con una firma válida, así que los clientes confían en ella y la instalan
  4. Llega a la vez a los entornos de muchos clientes: un ataque a la cadena de suministro

Caso real

En el caso SolarWinds, descubierto en 2020, se introdujo una puerta trasera (SUNBURST) en actualizaciones legítimas del software de gestión de TI Orion. Unas 18 000 organizaciones descargaron la actualización, entre ellas organismos del Gobierno de EE. UU.

Señales de alerta

  • Tras una actualización, el software empieza a comunicarse con servidores externos desconocidos
  • El proveedor o las autoridades anuncian un compromiso

Defensa: prevenir

  • Verificar la firma de código y también el origen y el hash de la actualización
  • Desplegar primero las actualizaciones importantes en un entorno de pruebas y observar su comportamiento y tráfico
  • Evaluar la seguridad de los proveedores y pedir una lista de materiales de software (SBOM)
  • Dar al software de gestión solo los privilegios y accesos de red imprescindibles

Defensa: detectar

  • El EDR y la monitorización de red detectan cambios de tráfico o comportamiento tras las actualizaciones
  • La supervisión de paquetes y la inteligencia de amenazas avisan pronto de actualizaciones comprometidas

Defensa: responder

  • Identificar, aislar y eliminar las versiones afectadas; seguir las indicaciones del proveedor
  • Cambiar las credenciales que podía usar el software y buscar indicios de intrusión

Clave para el examen

Idea clave: ni siquiera una actualización con firma válida está garantizada. Recuerda SolarWinds como el ejemplo típico de ataque a la cadena de suministro.

不正なSQL文でDBを操作する

Manipulates the database with malicious SQL

Manipula la base de datos con SQL malicioso

代表例ExamplesEjemplos
  • ' OR 1=1 --
  • 検索欄からの全件取得
  • ' OR 1=1 --
  • Dumping all records via a search box
  • ' OR 1=1 --
  • Extraer todos los registros desde un buscador
詳しく（仕組みと対策）Details: how it works & defensesDetalles: cómo funciona y defensas

仕組み

  1. アプリが、入力欄の値をそのままSQL文につなげてデータベースに問い合わせている箇所を探す
  2. 入力に SQL の記号を混ぜて送る。例：ログイン欄に ' OR 1=1 -- と入れると、条件が常に真になる
  3. データベースは改変されたSQL文を実行し、全件の読み出し、認証の回避、データの改ざん・削除が起きる

実例

2008年、米国の決済処理会社 Heartland Payment Systems は、SQLインジェクションを入口に社内ネットワークへ侵入され、約1億3千万件のカード情報が盗まれた。

兆候

  • Webログに '、OR 1=1、UNION SELECT などを含む要求が並ぶ
  • SQLのエラーメッセージが画面に出る
  • データベースから通常ありえない量のデータが読み出される

対策：予防

  • プリペアドステートメント（パラメータ化クエリ）を使い、入力を命令として解釈させない
  • 入力値検証（許可リスト方式）
  • アプリが使うDBアカウントを最小特権にする（全件削除などをできないようにする）
  • エラーメッセージに内部の詳細を出さない

対策：検知

  • WAF でSQLインジェクションのパターンを検知・遮断する
  • 動的アプリ分析（DAST）や侵入テストで、脆弱な入力欄を見つける

対策：対応

  • 脆弱な箇所を修正し、読み出された・改ざんされたデータの範囲を調べる
  • 個人情報が漏れた場合は、法令に従って報告・通知する

試験のポイント

' OR 1=1 -- が出てきたらSQLインジェクション。最も効く対策はパラメータ化クエリ、補助的に入力値検証と WAF。

How it works

  1. Find where the app pastes form input straight into a SQL statement sent to the database
  2. Send input mixed with SQL syntax — e.g., entering ' OR 1=1 -- in a login field makes the condition always true
  3. The database runs the altered statement: dumping every row, bypassing login, or altering or deleting data

Real-world case

In 2008, the US payment processor Heartland Payment Systems was breached through SQL injection, and about 130 million card numbers were stolen.

Warning signs

  • Web logs show requests containing ', OR 1=1, UNION SELECT and similar
  • SQL error messages appear on screen
  • Abnormally large amounts of data are read from the database

Defense: prevent

  • Use prepared statements (parameterised queries) so input is never interpreted as a command
  • Input validation (allow-list approach)
  • Give the app's database account least privilege (e.g., it cannot drop tables)
  • Don't expose internal details in error messages

Defense: detect

  • A WAF detects and blocks SQL injection patterns
  • Dynamic application testing (DAST) and penetration tests find vulnerable fields

Defense: respond

  • Fix the vulnerable code and determine what was read or altered
  • If personal data leaked, report and notify as the law requires

Exam tip

See ' OR 1=1 --? It's SQL injection. The most effective control is parameterised queries, backed up by input validation and a WAF.

Cómo funciona

  1. Buscar dónde la aplicación pega la entrada del formulario directamente en una sentencia SQL que envía a la base de datos
  2. Enviar entradas mezcladas con sintaxis SQL: por ejemplo, escribir ' OR 1=1 -- en el campo de usuario hace que la condición sea siempre verdadera
  3. La base de datos ejecuta la sentencia alterada: vuelca todas las filas, se salta el inicio de sesión o modifica y borra datos

Caso real

En 2008, el procesador de pagos estadounidense Heartland Payment Systems sufrió una intrusión a través de una inyección SQL y le robaron unos 130 millones de números de tarjeta.

Señales de alerta

  • Los registros web muestran peticiones con ', OR 1=1, UNION SELECT y similares
  • Aparecen en pantalla mensajes de error de SQL
  • Se leen cantidades anormalmente grandes de datos de la base de datos

Defensa: prevenir

  • Usar sentencias preparadas (consultas parametrizadas) para que la entrada nunca se interprete como orden
  • Validación de entradas (enfoque de lista de permitidos)
  • Dar a la cuenta de base de datos de la aplicación el mínimo privilegio (p. ej., que no pueda borrar tablas)
  • No mostrar detalles internos en los mensajes de error

Defensa: detectar

  • Un WAF detecta y bloquea patrones de inyección SQL
  • Las pruebas dinámicas de aplicaciones (DAST) y las pruebas de penetración encuentran campos vulnerables

Defensa: responder

  • Corregir el código vulnerable y determinar qué se leyó o modificó
  • Si se filtraron datos personales, informar y notificar según exija la ley

Clave para el examen

¿Ves ' OR 1=1 --? Es inyección SQL. El control más eficaz son las consultas parametrizadas, reforzadas con validación de entradas y un WAF.

仕組み

  1. 掲示板の投稿欄や検索結果など、利用者の入力をそのままページに表示する箇所を探す
  2. <script> タグなど、ブラウザで実行されるコードを入力に埋め込む
  3. ほかの利用者がそのページを開くと、その人のブラウザでスクリプトが動く
  4. Cookie（セッション情報）の窃取、なりすまし操作、偽のログイン画面の表示などが起きる

実例

2005年、MySpace に投稿された Samy ワームは、閲覧した人のプロフィールに自分自身をコピーする保存型XSSで、約20時間で100万人以上に広がった。

兆候

  • ページの表示内容に、見覚えのないスクリプトやリンクが含まれている
  • Webログに <script>、onerror=、javascript: を含む要求がある

対策：予防

  • 表示する前に、入力をエスケープ（出力エンコード）して、コードとして解釈させない
  • 入力値検証で不要な記号を受け付けない
  • CSP（コンテンツセキュリティポリシー）で、許可していないスクリプトの実行を禁じる
  • Cookie に HttpOnly 属性を付け、スクリプトから読めなくする

対策：検知

  • WAF でXSSのパターンを検知・遮断する
  • 動的アプリ分析（DAST）で、エスケープ漏れを見つける

対策：対応

  • 埋め込まれた悪意のある投稿を削除し、脆弱な箇所を修正する
  • 盗まれた可能性のあるセッションを無効化する

試験のポイント

XSSは閲覧者のブラウザでスクリプトが動く（サーバーのDBを直接狙うのは SQLインジェクション）。種類は反射型・保存型・DOMベース。対策は「出力エスケープ」「CSP」「HttpOnly」。

How it works

  1. Look for places that display user input as-is on a page — forum posts, search results
  2. Embed code the browser will run, such as a <script> tag, in the input
  3. When other users open that page, the script runs in their browsers
  4. It can steal cookies (session data), perform actions as the victim, or show a fake login form

Real-world case

In 2005 the Samy worm on MySpace, a stored XSS that copied itself onto the profile of anyone who viewed it, spread to over a million users in about 20 hours.

Warning signs

  • Unfamiliar scripts or links appear in a page's content
  • Web logs contain requests with <script>, onerror= or javascript:

Defense: prevent

  • Escape (output-encode) input before displaying it so it isn't treated as code
  • Input validation rejects unnecessary symbols
  • A Content Security Policy (CSP) blocks scripts that aren't allowed
  • Mark cookies HttpOnly so scripts can't read them

Defense: detect

  • A WAF detects and blocks XSS patterns
  • Dynamic application testing (DAST) finds missing escaping

Defense: respond

  • Remove the malicious stored content and fix the vulnerable code
  • Invalidate sessions that may have been stolen

Exam tip

XSS runs scripts in the visitor's browser (attacking the server's database directly is SQL injection). Types: reflected, stored, DOM-based. Controls: output escaping, CSP, HttpOnly.

Cómo funciona

  1. Buscar lugares que muestran la entrada del usuario tal cual en una página: mensajes de foros, resultados de búsqueda
  2. Incluir en la entrada código que el navegador ejecutará, como una etiqueta <script>
  3. Cuando otros usuarios abren esa página, el script se ejecuta en sus navegadores
  4. Puede robar cookies (datos de sesión), actuar en nombre de la víctima o mostrar un formulario de inicio de sesión falso

Caso real

En 2005, el gusano Samy de MySpace, un XSS almacenado que se copiaba en el perfil de quien lo veía, llegó a más de un millón de usuarios en unas 20 horas.

Señales de alerta

  • Aparecen scripts o enlaces desconocidos en el contenido de una página
  • Los registros web contienen peticiones con <script>, onerror= o javascript:

Defensa: prevenir

  • Escapar (codificar la salida) antes de mostrar la entrada para que no se trate como código
  • La validación de entradas rechaza símbolos innecesarios
  • Una Política de Seguridad de Contenido (CSP) bloquea los scripts no permitidos
  • Marcar las cookies como HttpOnly para que los scripts no puedan leerlas

Defensa: detectar

  • Un WAF detecta y bloquea patrones de XSS
  • Las pruebas dinámicas de aplicaciones (DAST) encuentran escapados que faltan

Defensa: responder

  • Eliminar el contenido malicioso almacenado y corregir el código vulnerable
  • Invalidar las sesiones que pudieron robarse

Clave para el examen

El XSS ejecuta scripts en el navegador del visitante (atacar directamente la base de datos del servidor es inyección SQL). Tipos: reflejado, almacenado y basado en DOM. Controles: escapado de salida, CSP, HttpOnly.

詳しく（仕組みと対策）Details: how it works & defensesDetalles: cómo funciona y defensas

仕組み

  1. 攻撃者は、自分が操作できる仮想マシン（ゲスト）を手に入れる。クラウドなら契約するだけで用意できる
  2. ハイパーバイザーや仮想デバイス（仮想ディスク・ネットワーク機器など）の脆弱性を突く
  3. VMの隔離を突破して、ホスト（ハイパーバイザー）でコードを実行する
  4. 同じホスト上のほかの仮想マシン（他の利用者のものを含む）にアクセスできるようになる

実例

2015年に公表された VENOM（CVE-2015-3456）は、QEMU などで使われる仮想フロッピーディスク装置の脆弱性で、ゲストからホスト上でコードを実行できるおそれがあった。多くのクラウド事業者が緊急でパッチを当てた。

兆候

  • ハイパーバイザー上で、想定外のプロセスや通信が発生する
  • ゲストVMから、仮想デバイスへの異常な操作が大量に行われる

対策：予防

  • ハイパーバイザーと仮想化ソフトに素早くパッチを当てる
  • 使わない仮想デバイス（仮想フロッピーなど）を無効化する
  • 機密度の異なるシステムは別のホストに置き、隔離を強める
  • ハイパーバイザーの管理インターフェースを分離したネットワークに置く

対策：検知

  • ハイパーバイザーのログと振る舞いを監視する
  • クラウド事業者のセキュリティ情報を確認する

対策：対応

  • 影響を受けるホストを特定してパッチを当て、そのホスト上のVMに侵害の痕跡がないか調べる

試験のポイント

VM内からホストへ抜け出すのがVMエスケープ。影響が同じホストの全VMに及ぶので深刻。対策の中心はハイパーバイザーのパッチ。

How it works

  1. The attacker gets a virtual machine (guest) it controls — in the cloud, simply by signing up
  2. It exploits a vulnerability in the hypervisor or a virtual device (virtual disk, network adapter...)
  3. It breaks out of the VM's isolation and runs code on the host (hypervisor)
  4. From there it can reach other VMs on the same host, including other customers'

Real-world case

VENOM (CVE-2015-3456), disclosed in 2015, was a flaw in the virtual floppy controller used by QEMU and others that could let a guest run code on the host. Many cloud providers patched urgently.

Warning signs

  • Unexpected processes or traffic on the hypervisor
  • A guest VM performs huge numbers of abnormal operations on virtual devices

Defense: prevent

  • Patch hypervisors and virtualisation software quickly
  • Disable unused virtual devices (such as virtual floppy drives)
  • Put systems of different sensitivity on separate hosts to strengthen isolation
  • Keep hypervisor management interfaces on a separate network

Defense: detect

  • Monitor hypervisor logs and behaviour
  • Follow your cloud provider's security bulletins

Defense: respond

  • Identify and patch affected hosts; check the VMs on them for signs of compromise

Exam tip

VM escape means breaking out of a VM onto the host. It's serious because every VM on that host is exposed. The core control is patching the hypervisor.

Cómo funciona

  1. El atacante consigue una máquina virtual (invitada) que controla; en la nube, basta con contratarla
  2. Aprovecha una vulnerabilidad del hipervisor o de un dispositivo virtual (disco virtual, adaptador de red...)
  3. Rompe el aislamiento de la VM y ejecuta código en el anfitrión (hipervisor)
  4. Desde allí puede llegar a otras VM del mismo anfitrión, incluidas las de otros clientes

Caso real

VENOM (CVE-2015-3456), publicado en 2015, fue una vulnerabilidad del controlador de disquete virtual que usan QEMU y otros, que podía permitir a una invitada ejecutar código en el anfitrión. Muchos proveedores de nube aplicaron parches con urgencia.

Señales de alerta

  • Procesos o tráfico inesperados en el hipervisor
  • Una VM invitada realiza enormes cantidades de operaciones anómalas sobre dispositivos virtuales

Defensa: prevenir

  • Parchear con rapidez el hipervisor y el software de virtualización
  • Desactivar los dispositivos virtuales que no se usen (como las disqueteras virtuales)
  • Situar los sistemas de distinta sensibilidad en anfitriones separados para reforzar el aislamiento
  • Mantener las interfaces de gestión del hipervisor en una red aparte

Defensa: detectar

  • Supervisar los registros y el comportamiento del hipervisor
  • Seguir los boletines de seguridad del proveedor de nube

Defensa: responder

  • Identificar y parchear los anfitriones afectados; revisar sus VM en busca de indicios de compromiso

Clave para el examen

El escape de VM consiste en salir de una VM al anfitrión. Es grave porque quedan expuestas todas las VM de ese anfitrión. El control principal es parchear el hipervisor.

  • Reasignación de memoria sin borrar
詳しく（仕組みと対策）Details: how it works & defensesDetalles: cómo funciona y defensas

仕組み

  1. クラウドや仮想化では、メモリ・ディスク・GPU などの資源を、使い終わった利用者から別の利用者へ再割り当てする
  2. 前の利用者のデータが消去されないまま残っていると、次の利用者がそれを読み出せる
  3. 攻撃者は、新しく割り当てられた資源の中身を読み、他人の機密データや鍵を探す

実例

2024年に公表された LeftoverLocals（CVE-2023-4969）では、一部のGPUで、ある処理が使ったメモリが消去されずに残り、別のプロセスから読み出せることが示された。他の利用者の生成AIの応答を盗み見られる危険があった。

兆候

  • 新しく割り当てたディスクやメモリに、ゼロ以外の古いデータが入っている
  • クラウド事業者から、資源の分離に関する脆弱性の発表がある

対策：予防

  • 保存データを暗号化し、資源を解放する前に鍵を破棄する（暗号学的消去）
  • 資源の解放時・割り当て時にゼロで上書きする（サニタイゼーション）
  • 機密性の高い処理には専用のホストやインスタンスを使う
  • 責任共有モデルで、消去が事業者と自社のどちらの責任かを確認する

対策：検知

  • 事業者のセキュリティ情報を監視し、影響を受ける資源を把握する

対策：対応

  • 影響を受けた資源上のデータと鍵を洗い出し、必要に応じて鍵やパスワードを変更する

試験のポイント

リソースの再利用は、再割り当てされた資源に前の利用者のデータが残る問題。対策のキーワードは「暗号化」「サニタイゼーション（消去）」「専用インスタンス」。

How it works

  1. In cloud and virtualised environments, memory, disk and GPU resources are reassigned to another tenant after one finishes
  2. If the previous tenant's data is not wiped, the next tenant can read it
  3. An attacker reads newly assigned resources, looking for other people's sensitive data or keys

Real-world case

LeftoverLocals (CVE-2023-4969), disclosed in 2024, showed that on some GPUs memory used by one process was not cleared and could be read by another. It risked exposing other users' generative-AI responses.

Warning signs

  • Newly allocated disks or memory contain old, non-zero data
  • The cloud provider announces a vulnerability in resource isolation

Defense: prevent

  • Encrypt stored data and destroy the key before releasing resources (crypto-erase)
  • Overwrite resources with zeros on release or allocation (sanitisation)
  • Use dedicated hosts or instances for highly sensitive workloads
  • Check in the shared responsibility model whether wiping is the provider's job or yours

Defense: detect

  • Follow the provider's security bulletins to identify affected resources

Defense: respond

  • Identify data and keys on affected resources; rotate keys and passwords where needed

Exam tip

Resource reuse is the problem of a previous tenant's data remaining in reassigned resources. Control keywords: encryption, sanitisation (wiping), dedicated instances.

Cómo funciona

  1. En la nube y la virtualización, la memoria, el disco y la GPU se reasignan a otro cliente cuando uno termina
  2. Si los datos del cliente anterior no se borran, el siguiente puede leerlos
  3. Un atacante lee los recursos recién asignados en busca de datos sensibles o claves de otros

Caso real

LeftoverLocals (CVE-2023-4969), publicado en 2024, mostró que en algunas GPU la memoria usada por un proceso no se borraba y podía leerla otro. Existía el riesgo de exponer las respuestas de IA generativa de otros usuarios.

Señales de alerta

  • Los discos o la memoria recién asignados contienen datos antiguos distintos de cero
  • El proveedor de nube anuncia una vulnerabilidad en el aislamiento de recursos

Defensa: prevenir

  • Cifrar los datos almacenados y destruir la clave antes de liberar los recursos (borrado criptográfico)
  • Sobrescribir con ceros los recursos al liberarlos o asignarlos (sanitización)
  • Usar anfitriones o instancias dedicados para las cargas muy sensibles
  • Comprobar en el modelo de responsabilidad compartida si el borrado corresponde al proveedor o a ti

Defensa: detectar

  • Seguir los boletines de seguridad del proveedor para identificar los recursos afectados

Defensa: responder

  • Identificar los datos y claves en los recursos afectados; rotar claves y contraseñas cuando sea necesario

Clave para el examen

La reutilización de recursos es el problema de que queden datos del cliente anterior en recursos reasignados. Palabras clave de los controles: cifrado, sanitización (borrado), instancias dedicadas.
