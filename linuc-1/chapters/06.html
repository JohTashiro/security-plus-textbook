06 プロセス管理

サービスが重い・応答しない・ゾンビが残る——現場の多くはプロセス観察から始まります。監視、優先度、シグナル、ジョブ制御の続きを実務単位でまとめます。

1. プロセスを見る

ps aux
ps -ef
ps -u alice
pstree -p
pgrep -a sshd
pidof nginx
コマンド 用途
ps スナップショット
top / htop 対話的な監視（htop は環境による）
pgrep 名前などから PID を探す
uptime 負荷平均の手がかり 
top
# よく使うキー: q 終了、k kill、P CPU順、M メモリ順（実装差あり）

見るポイント: PID、親（PPID）、CPU％、メモリ、状態（R/S/D/Z）、起動コマンド。

2. フォアグラウンド／バックグラウンド

第03章の続きです。

long_job &
jobs
fg %1
bg %1

ログアウト後も続けたい場合:

nohup ./job.sh &
# または tmux / screen 内で実行（11.0でもセッション継続は重視）

3. シグナルと終了

kill PID
kill -15 PID          # SIGTERM（丁寧な終了依頼）
kill -TERM PID
kill -9 PID           # SIGKILL（強制。最後の手段）
kill -HUP PID         # 設定再読み込みに使うデーモンも多い
killall process_name
pkill -f pattern
信号 典型
TERM (15) まずこれ
KILL (9) 捕まらない。状態保存なし
HUP (1) 再読込や端末切断の文脈
STOP / CONT 一時停止と再開

-9 を常用しない。アプリのクリーンアップや子プロセス整理を飛ばすためです。

4. 優先度（nice / renice）

CPU 時間の分け前に影響する「やさしさ」です。値が大きいほど控えめ（優先度が低い）。

nice -n 10 ./batch.sh
renice -n 5 -p PID
ps -o pid,ni,cmd -p PID

root 以外が優先度を上げる（nice を下げる）には制限があります。バッチ処理を nice 付きで走らせるのが定番パターンです。

※ Version 10.0 の公式から「実行優先度変更」単独項目は薄まりましたが、プロセス管理の実務として残します。監視・シグナルが主、nice は補助、という比重で十分です。

5. 負荷と切り分け

uptime
free -h
ps aux --sort=-%cpu | head
ps aux --sort=-%mem | head

型:

  1. uptime / top で CPU・負荷・待ち
  2. 犯人候補の PID を特定（pgrep / ps）
  3. ログをテキスト処理（第05章）
  4. 必要なら TERM → 待って → KILL
  5. 再発するならサービス設定・リソース制限・バグを疑う

D 状態（uninterruptible sleep）が続く場合は、ディスクや NFS など I/O 側を疑うことが多いです。Z（ゾンビ）は親が wait していない印で、親の再起動が効くことがあります。

6. 現場チェック

  • [ ] ps / top / pgrep で対象 PID を特定できる
  • [ ] kill で TERM と KILL の違いを説明できる
  • [ ] jobs / fg / bg / nohup または tmux を使える
  • [ ] nice でバッチを控えめに起動できる
  • [ ] CPU 高騰時に「誰が・何を」まで辿れる

確認例:

pgrep -a python
ps -fp $(pgrep -d, nginx)
kill -0 PID    # 存在確認（シグナルは送らない）
