09 運用 自動化 AI

手作業の CLI だけでも小規模は回りますが、台数と変更頻度が増えるとミスと遅延が支配的になります。この章では管理アプローチ、コントローラ／SDN の見方、REST／JSON、Ansible、AI 支援の読み方を実務単位で押さえます。

1. 自動化が運用に与える影響

観点 人手中心 自動化寄り
再現性 人によって差 同じ手順を何度でも
速度 台数に比例して遅い 並行・一括が可能
監査 履歴が散らばりやすい コード／ジョブとして残せる
リスク 打ち間違い 悪い Playbook の一括適用

自動化は「人が考えなくてよい」ではなく、意図をコード化し、検証してから適用するための手段です。

2. 管理アプローチの比較

v2.0 で明示される管理の切り口（「v2.0で特に重視」）:

アプローチ イメージ
Device-based 機器ごとにログインして設定
Cloud-based クラウド上の管理面から操作
Controller-based コントローラがポリシーを配布
Automation-based スクリプト／オーケストレータで実行
Infrastructure as Code（IaC） 望ましい状態をファイルで定義

従来型（機器個別）とコントローラベースを対比すると、制御プレーンの集中度と、ポリシーの一貫性が変わります。

3. コントローラベース／SDN の用語

用語 意味のイメージ
Underlay 物理・ルーティングの土台
Overlay その上に張る論理ネットワーク
Fabric 一体として動くスイッチ群の枠
Control plane / Data plane 制御の頭脳と転送の手足
Northbound API コントローラ ← 上位アプリ／オーケストレータ
Southbound API コントローラ → 機器

「どこが頭脳で、どこが転送か」「誰が誰を API で呼ぶか」を図で説明できれば十分です。

4. REST API と JSON

REST ベース API の感覚:

要素 内容
HTTP 動詞 GET（読）／POST（作）／PUT・PATCH（更）／DELETE（削）
CRUD Create / Read / Update / Delete
認証 トークン、Basic、証明書など
データ 多くが JSON

JSON の構成要素の読み方:

{
  "hostname": "sw-edge-01",
  "vlans": [10, 20, 30],
  "up": true
}
要素 例
オブジェクト { ... }
配列 [ ... ]
文字列 / 数値 / 真偽 "sw-edge-01" / 10 / true
キーと値の組 "hostname": "..."

試験・現場とも、「この JSON の hostname は何か」「vlans は配列か」が読めれば足場になります。

5. 構成管理（Ansible / Terraform）

ツール ざっくりした役割
Ansible エージェントレスで手順（Playbook）を実行し設定を当てる
Terraform 望ましいインフラ状態を宣言し、差分を適用する（IaC）

v1.1 は「能力を識別」、v2.0 は Ansible などでコマンドを実行する寄りの表現です（「v2.0で特に重視」）。CCNA では深い Jinja やモジュール暗記より、inventory／playbook／冪等性（何度実行しても意図した状態へ）の言葉が使えれば十分です。

簡易イメージ（概念）:

- name: ensure SSH banner
  hosts: switches
  tasks:
    - name: set banner
      ios_banner:
        banner: login
        text: |
          Authorized only

6. 監視との接点（SNMP / syslog）

第07章の続きとして、運用章では「誰が何を見るか」に焦点を当てます。

  • SNMP: 監視サーバが機器状態を取得する枠組み
  • syslog: イベントを重大度・ファシリティ付きで送る

v2.0 は syslog の 内容・severity・facility の解釈 と SNMP の役割を運用ドメインに置いています。

7. AI とネットワーク運用

生成型・予測型・機械学習

種類 運用でのイメージ
Generative AI 文章・設定案・要約の生成
Predictive 障害予兆や容量の予測
Machine learning データからパターンを学習

Agentic AI（v2.0で特に重視）

単発の回答だけでなく、目標に向けてツール呼び出しや手順提案を連鎖する AI エージェントの役割です。試験説明では、agentic AI やデジタルネットワークアシスタントの出力・推奨を評価する設問があり得るとされています。現場でも「提案を鵜呑みにせず、変更前後の根拠と影響範囲を人が検証する」が基本です。

プロンプトの構成要素（v2.0で特に重視）

生成 AI に送る指示を選ぶとき、次を意識します。

要素 例
Data classification 社外秘設定を貼らない、マスクする
Output format 「表で」「IOS コマンドのみ」
Persona 「現場のネットワーク運用者として」
Instructions 「変更は提案のみ。適用手順は分けて書く」

悪い例: 本番の全設定とパスワードをそのまま貼る。
良い例: 匿名化した show 抜粋と、欲しい出力形式・制約を明示する。

8. 現場チェック

  • [ ] 自動化の利点と一括適用リスクを説明できる
  • [ ] device / controller / automation / IaC の違いを言える
  • [ ] underlay / overlay、northbound / southbound を図示できる
  • [ ] REST の GET と POST の違い、JSON のオブジェクトと配列を読める
  • [ ] Ansible が「手順実行」、Terraform が「状態宣言」寄りであることを説明できる
  • [ ] 生成 AI プロンプトで機密・形式・役割・指示を分けられる
  • [ ] agentic AI の提案を人間が検証する理由を言える

ラボ／演習例:

  • 小さな JSON を読み、特定キーの値を口頭で答える
  • 匿名化したインタフェース障害の症状から、生成 AI 用プロンプトを1つ書く（機密を入れない）
